# 重複・類似データの整理

最終更新: 2026-07-26

## 目的

同じ項目や日本語案が表記だけを変えて重複することを防ぎ、意味が近い案は利用場面の
違いを説明できる状態にする。初期データの自動統合はせず、説明、合う場面、例文を
確認してから修正または併存を判断する。

## 監査方法

空のSQLiteデータベースへ `prisma/seed.ts` を投入し、`npm run audit:data` で次を確認した。

- 項目名を全半角、空白、中黒、ハイフン、大小文字の違いを除いて比較する。
- 元の外国語を同じ方法で比較し、別の項目に同じ原語が登録されていないか確認する。
- 同じ使われ方に、正規化後に同じ日本語案がないか確認する。
- 異なる項目に、正規化後に同じ日本語案がないか確認する。
- 編集距離による類似度が0.66以上の日本語案を、意味と利用場面の目視確認対象にする。

機械判定は候補の抽出に使い、意味の近さは説明、合う場面、例文を読んで編集判断する。

## 結果

| 確認項目 | 初回 | 整理後 |
|---|---:|---:|
| 正規化後に重複する項目名 | 0件 | 0件 |
| 同じ原語を持つ別項目 | 0件 | 0件 |
| 同じ使われ方の重複案 | 0件 | 0件 |
| 異なる項目で完全一致する日本語案 | 3組 | 0組 |
| 表記が近く、継続確認する日本語案 | - | 2組 |

### 完全一致していた3組

| 変更前 | 対象 | 判断と変更 |
|---|---|---|
| 対応項目 | タスク / アクションアイテム | タスク側を「作業項目」に変更。作業一覧の一単位と、担当・期限を持つ会議後の対応を分けた。 |
| 接点 | チャネル / タッチポイント | チャネル側を「受付経路」に変更。情報を届ける経路と、顧客が触れる個別の場面を分けた。 |
| 提供開始 | ローンチ / リリース | リリース側を「提供」に変更。最初に世に出す開始と、完成した機能を利用可能にする行為を分けた。 |

各変更に合わせて、合う場面、理由、使用例も修正した。

### 表記が近いが併存する2組

| 候補 | 併存する理由 |
|---|---|
| インクルージョン「受け入れ」 / オンボーディング「受け入れ支援」 | 前者は排除せず参加できる状態、後者は新任者・利用者が始めるときの具体的支援を指す。 |
| タスク「作業」 / バックログ「作業残」 | 前者は行うべき作業そのもの、後者は未着手・未処理の作業を集めた一覧を指す。 |

完全一致ではなくても意味が混同されやすいため、今後も `npm run audit:data` の
目視確認対象として表示する。

### 関連概念として併存する項目

- ローンチ / リリース: 初公開・立ち上げと、版や機能の提供を分ける。
- チャネル / タッチポイント: 届ける経路と、顧客が触れる個別の場面を分ける。
- タスク / アクションアイテム / バックログ: 作業、会議後の担当事項、未処理一覧を分ける。
- アクセシビリティ / ユーザビリティ: 利用できる条件の公平性と、操作のしやすさを分ける。

これらは項目統合を行わず、説明と利用場面の境界を維持する。

## 継続運用

1. 項目追加前に、項目名と元の外国語で既存項目を検索する。
2. 完全一致する日本語案が別項目にある場合は、説明と例文で意味の差を確認する。
3. 差を説明できない案は統合または改名し、差がある案は合う場面と理由を具体化する。
4. 初期データ更新後は空のDBで `npm run audit:data` を実行する。
5. 類似候補が増えた場合はこの文書に判断を追記する。
